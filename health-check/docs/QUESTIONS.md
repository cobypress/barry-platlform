A first real call must show: that the request is accepted (no 400 on `effort` or the format); `stop_reason` `end_turn` and not `max_tokens`, since thinking counts against the 1,024; the usage's input and output tokens for a class of about 100,000 characters, the largest we send; and that the reply parses as `{ summary }` with nothing else.
b) How often the guard refuses real code. A prompt is refused, and counted as refused, when the name check still finds part of a known person's name, an id of theirs or an email after masking. Code is full of words that are also names (`Case`, `Will`, `Mark`, a field called `Owner_Name__c`), and the guard masks a capitalised one only where it matches a person in the run's user list. How many of a real org's 200 are refused, and are they refused for a person's name or for a word that only looks like one? Hard-coded record ids are masked as `[[id]]` by the route itself: the guard knows only the ids of people the run labelled, so any other id would otherwise have gone as it was. Any 15- or 18-character word with a digit in it is masked, which may mask a few that aren't ids.
c) How long 200 calls take. They run one after another, before the report sections are drafted, inside the run job. A run job has no time limit of its own: BullMQ holds the heavy slot's lock for 10 minutes (`HEAVY_LOCK_MS`) and renews it while the process lives, so only a process that dies loses the job, and then each summary already made is kept in `handbook-summaries.partial.jsonl` and not paid for again. At a few seconds a call that is ten minutes or more of a run's time, with the sections waiting behind it. How long do they take, and does the console's "analysing" need to say so?
d) How often a real summary is not written. A reply is refused for any figure (a digit is allowed only inside a name the code holds, so "a class that retries three times" is not written), a link, a full stop between two letters or digits (a host, a field path such as `Account.Name`, and "e.g." too), anything in double square brackets, a line break, a character a Word file can't hold (a control character, U+FFFE or U+FFFF, a lone surrogate), more than 80 words, or a name. How many of 200 are not written after the one retry, and for which reason most often?
e) The longest name Salesforce allows. An Apex class's or trigger's name is at most 40 characters, as we understand it, and `nowhere-else.test.ts` plants one that long. The summaries file allows 255, the console's own limit (decision 493), and the route leaves out, as not written, a name longer than that, so nothing it writes can break the console's reader whatever the limit is.
f) Does a class's `LengthWithoutComments` come back for every class and trigger, including those Salesforce withholds (`(hidden)`)? The 200 kept are the largest by it, ties by kind then name, and a missing one counts as 0, so it's kept only if there's room after the rest.
g) The worker's SQL for the summaries has never run against a real Postgres: the tests hold its text and the transaction's shape (`postgres-store.test.ts`), and the memory store its rules. A first real run, against a database branch with the console's `20261122_health_check_handbook_summaries.sql` applied, must show: a run's first save writes one row, `waiting`, `decidedBy` and `decidedAt` NULL, every item `struck: false`, and the table's three CHECKs accept it; a second save while it waits replaces its model, time, items and counts and clears its strikes; a second save after the console approved or left it out leaves it as it was, with no error and a row count of 0 (what `ON CONFLICT … DO UPDATE … WHERE` should do); `items` and `leftOut` go in as text cast `::jsonb` and come back from `pg` as parsed JSON, and `madeAt` comes back through `to_char` in the form the console's `Timestamp` takes. A console without the table: the insert fails with 42P01 inside the `handbook_summaries` savepoint, `ROLLBACK TO SAVEPOINT` leaves the transaction usable, and the run's other rows commit, which the facts' savepoint already relies on. The foreign key to the run (23503) shouldn't fire, since the run's row is locked `FOR UPDATE` in the same transaction. Any error on the statement, 42P01 or not, goes back to the savepoint and the run's other rows commit, logged by its SQLSTATE: a first run should show that Postgres takes `ROLLBACK TO SAVEPOINT` after a constraint error (23514, 23503) and after jsonb refusing a character (22P05) alike. The save leaves out a summary holding U+0000 or a lone surrogate before it builds the row, so 22P05 should never come; one that does means the check and Postgres disagree on a character.
h) The documents job reads the row with the switch on, the same way. A first make from a released run with an approved row must show the summaries under their entries in the Word file in the customer's Drive, and one with a waiting or left-out row, or none, a handbook the same as before. The run is released before its documents are made, and the console can't reopen the row once a run is released (decision 493), so what is printed is what was approved; a remake prints the row as it is then.
i) Is a class's name in `handbook.json` always spelt as `apex-source.json` spells it? Both come from the same Apex rows, `NamespacePrefix = null`, so they should be; a summary is printed only against an exact match of kind and name. Apex names are unique within a kind in an org without regard to case, so two entries of one kind can't share a name from a real read; one that did would print neither summary. A class and a trigger can share a name, and each prints only its own kind's summary.
