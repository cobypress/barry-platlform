# Decisions

Newest thinking is in the rationale, not the order. Change a decision by editing it here and saying why.

| # | Decision | Why |
| --- | --- | --- |
| 1 | Node 24 runs TypeScript directly, with no build step | Matches `node --test` in the site, and means one less artefact. Needs a host on Node 24 (see QUESTIONS.md) |
| 2 | Plain `fetch` behind our own client, not jsforce | A library brings write methods we'd then have to prove unreachable. One send path is easy to audit and test |
| 3 | Allowlist by route and operation, not by HTTP method | GETs can run Apex, and POSTs can read. See ARCHITECTURE.md |
| 4 | `listMetadata`, `readMetadata` and `describeMetadata` are refused for now | Nothing uses them. Each read we add is a deliberate change with a test |
| 5 | No Bulk API yet | A bulk query is a POST that creates a job, so it widens the boundary. REST paging covers development orgs. Revisit for large orgs in Milestone 3 |
| 6 | Metadata retrieve over per-flow Tooling reads | One retrieve costs a few calls. Tooling costs one call per flow, because `Metadata` is single-row |
| 7 | Default budget stop at 50% of the org's daily limit, with a 5,000-call cap per run | The customer's integrations keep the larger share. Set by `--budget-share` or `HC_API_BUDGET_SHARE` |
| 8 | Unknown guards block exactly as failed guards do | A guard we couldn't run has told us nothing |
| 9 | Guards are enforced twice: engine and schema | A rule author can't bypass them by mistake |
| 10 | The Default Workflow User is a manual step | We couldn't confirm it's readable by API. Until it's answered, no licence removal is recommended. Confirm on the development org, and automate it if it can be read |
| 11 | Field removal is only recommended if no report uses the field, every report was read, and no private report is out of reach | Other people's private reports can't be read, so any that exist leave the guard unknown, and unknown blocks (rule 3). Most orgs have some, so field removal will usually stay "investigate". See QUESTIONS.md |
| 12 | Dashboard use is not measurable | `LastViewedDate` is per user. The obvious query would call a dashboard the whole team uses "unused" |
| 13 | No decision is separate from lost | Both win rates are reported, because deals that fizzle out would distort a single figure |
| 14 | A deal's close time comes from stage history, using its final closed run | Handles reopened deals, and CloseDate is often edited. CloseDate is the declared fallback |
| 15 | Conversion counts a skipped stage as passed, and reports skips separately | Otherwise a skipped stage shows as impossible conversion above 100% |
| 16 | Medians, not means, for time metrics | One stuck deal shouldn't move the headline |
| 17 | Multi-currency orgs get not measurable on value metrics | Adding amounts in mixed currencies is wrong. Supplying historic rates is future work. Counts still run |
| 18 | Days, months and quarters use the org's time zone, with UTC as a stated fallback | A close late on 31 March Pacific belongs in March. Instants are converted, and date-only fields such as CloseDate are left alone, because converting one would move it. The analysis window itself is still set in UTC in `run.ts`, so its edge can differ by a day. Every metric says which calendar it's on |
| 19 | Pseudonym tokens are assigned in user id order, per run | Stable within a run. Findings line up across runs by finding id, not token |
| 20 | One-word names aren't scrubbed from free text | "Sales" would turn Sales Cloud into a token. They're still tokenised wherever the engine labels a user |
| 21 | Fixtures are generated by running the real engine against a simulator | Hand-written JSON drifts. The simulator refuses SOQL it doesn't know, and replay refuses unrecorded requests |
| 22 | Ban-list tests aren't used for customer data | A list of customer names would itself put them in the repo. Tests require reserved domains and zero-padded ids instead |
| 23 | The CLI needs `HC_APPROVED_ORG_ALIASES`, empty by default | This machine has customer orgs logged in. One typo must not reach them |
| 24 | The CLI refuses to write inside a git work tree | Rule 8. Run folders hold CRM rows |
| 25 | Black Cloud's design system was readable at the artifact link | Colours and type match the brief. Tokens live in `src/design/tokens.ts`, checked against `colors_and_type.css`: brand colours match exactly, and muted text and hairlines use its neutrals. It has nothing for Carbon, so the two chart panel tints are ours |
| 26 | Recommended file storage: AWS S3 in `eu-west-2` (London) | See below |
| 27 | The fiscal year comes from the org unless the calibration sets it | A silent January default would give an April-start org the wrong quarters. A mismatch is raised as a finding, and if neither is readable, quarters aren't reported |
| 28 | Deals created already closed count in win rate, but not in conversion, sales cycle or slippage | They're real outcomes with no sales process behind them. Counting won ones as passing every stage while dropping lost ones inflated conversion |
| 29 | The Opportunity extract includes anything modified in the window, or in a calibrated open stage | Otherwise a bulk close of old deals vanishes, inflating win rate and undercounting past pipeline. `IsClosed` alone would let Salesforce decide what's open |
| 30 | A month end is judged on its own history gap (20%) and blank amounts (20%) | One old history row made months before a migration look measured |
| 32 | New reads for security: `SecurityHealthCheck` and `SecurityHealthCheckRisks` (Tooling), `PermissionSet`, `PermissionSetAssignment`, and `ApiType`, `Application` on `LoginHistory`, and sharing defaults on `Organization` | All are SOQL through existing routes, so the allowlist is unchanged. `OauthToken` isn't read, because it holds an authorisation code |
| 33 | New reads for current pipeline: `AccountId` on Opportunity, ids of open deals with `NextStep` filled, `ForecastingType`, `ForecastingQuota` | Text is read as filled or empty by filtering, so it's never fetched |
| 34 | New reads for forecast: `Period`, `ForecastingItem`, `ForecastingFact`. Forecast accuracy is not measurable | These rows are today's position, so they can't show what was called at the time |
| 35 | New reads for activity: `Task`, `Event`, `EmailMessage`, ids and dates only, for the last 365 days. `queryAll` stays off the allowlist | Archived activities need `queryAll`. A year of history is enough to start, and text fields are never selected |
| 36 | New reads for the lead funnel: `Lead`, `LeadHistory` (status changes, no values), `Campaign`, `CampaignMember`. Ids, dates, source and cost only | A funnel is counts and dates. Names, emails, phones, companies and campaign names are never selected |
| 37 | Every metric is not measurable when Opportunity can't be read, including ones that don't need it | `run.test.ts` pins this, and the rule against weakening tests decides it. It only matters when the pipeline report has already failed. See `docs/overnight/domains.md` |
| 38 | New read for revenue opportunities: `Account` id, owner and last activity, for accounts with a won deal | The name isn't read. Sized figures use only the org's own win rate, stated as a ceiling |
| 39 | New reads for report scanning: `Report` developer name and owner, `Folder`, a count of `Report USING SCOPE allPrivate`, and a Metadata retrieve of `Report` by name | The retrieve is an existing allowed operation, so the allowlist is unchanged. Only field names are kept: titles and filter values are dropped, because they can hold customer data |
| 40 | A domain's score is total earned over 8 times the rules counted. A pass earns 8, and an issue earns 8 minus its severity times its confidence factor | Each rule has a fixed maximum, so severity counts even with no passes. Earned over earned plus lost gave 0 to any domain with no passes, so five low issues scored the same as five critical ones |
| 41 | `LoginHistory`, `ForecastingItem` and `Campaign` are described before they're queried, in a `field-describe` step that checkpoints each describe. Optional fields the org lacks are dropped from the SELECT and listed in `missingFields` on the source, and only rules that need one are not measurable. A missing required field or object makes the source unavailable without a query. A failed describe falls back to the full query | A wrong field fails the whole query, so one feature-dependent field made every rule on that source not measurable. These three hold fields that depend on edition or features. Describe was already on the allowlist. Tooling objects can't be described this way, because Tooling describe isn't allowed |
| 42 | Field names follow the API 68.0 guides: Tooling `Layout` uses `EntityDefinitionId`, and `ApexTrigger` is read through REST, not Tooling | The Tooling reference doesn't list `TableEnumOrId` on `Layout`, or `Name`, `TableEnumOrId` and `NamespacePrefix` on `ApexTrigger`. The Object Reference lists all six trigger fields. See QUESTIONS.md |
| 43 | The 90-day plan holds 8, 10 and 10 actions, which is our working figure. Each action goes into the earliest month its severity and effort allow that still has room. Critical and high fixes that take up to medium effort can start in month one, and so can medium fixes that take very little. Large work starts in month three, or month two if it is critical. Low-severity work waits until month three. Whatever doesn't fit is listed after 90 days | Phasing by effort alone put 47 of 66 sample actions into the first month. Coby asked for my recommendation on 3 Nov |
| 44 | A domain gets a score only when at least 2 checks, and at least half its checks, could be measured | On the first live run, one calibration check scored historic pipeline 100 while every pipeline metric was not measurable. A score that rests on almost nothing misleads, so the domain says why it has no score instead (rule 5) |
| 45 | `hc benchmark` adds a run to the benchmark set only with `--consent`, once per run, recorded in the run folder as `benchmark-consent.json`. Rows are built from a fixed allowlist in `src/benchmark/export.ts`: measured domain scores, org-wide pipeline, activity and lead rates and days from `metrics.json`, and org-wide rates that data quality, best practice, utilisation and security checks record on a pass and an issue alike. Segments, series, stats, counts and amounts are never read. Industry comes from a fixed list of nine. The user band counts active standard users, leaving out accounts calibrated as shared, system, integration or test. The deal size band uses the median amount of won deals closed in the window, with no amount or zero left out, and is refused for multi-currency orgs or below `minSample` won deals. The period is the calendar quarter of the window end. Both bands are read from the raw extracts, so a purged run can't be exported | Rule 11. A row must not lead back to a customer, so it carries no run id, date or path, and the consent sits with the customer's own data instead. A figure only some orgs record (say, on an issue) would skew the set. Calendar quarters line up across orgs where fiscal ones don't. The bands aren't analysis outputs, and we'd rather refuse than guess (rule 5) |
| 46 | `hc purge` deletes a run's `checkpoints/` folder and nothing else, then writes `purged.json`. It refuses a folder without a valid `run.json`, and checkpoints that are a link. `--older-than` sweeps a runs folder by run date (`asOf`), skipping links and runs already purged | Raw extracts go 30 days after delivery. Findings, metrics, scores, calibration and the pseudonym map stay, so `hc render` still works: it never reads checkpoints. Delivery isn't recorded yet, and the run date comes first, so purging by it is never later than purging by delivery |
| 31 | The instance URL is parsed, and must be a bare https Salesforce host, on connect and refresh | A prefix check passes `https://x.salesforce.com@evil.example`, which sends the token to evil.example |

## File storage

We recommend **AWS S3 in eu-west-2 (London)**, with default KMS encryption, Block Public Access on, and a lifecycle rule that deletes extracts 30 days after delivery.

- **Region:** London keeps data in the UK, which is the simplest story for a UK customer's security review.
- **Fits Vercel:** the browser uploads screenshots straight to S3 through a presigned URL, so the file never passes through a function's request size limit. The worker reads with its own credentials.
- **Deletion:** a lifecycle rule enforces the retention promise even if our own code fails.

Alternatives considered:

- **Vercel Blob:** private stores and region choice exist, but we couldn't confirm a London store, and the region can't be changed afterwards. Reads also go through a function.
- **Cloudflare R2 with EU jurisdiction:** a good fallback if AWS isn't wanted, but it's EU rather than UK.

## Report decisions

Kept apart from the table above so the overnight branches merge cleanly.

| # | Decision | Why |
| --- | --- | --- |
| R1 | The number check matches value and unit, and blocks whatever it can't read | An invented figure is the worst failure this product has. A false alarm only costs a redraft |
| R2 | A rounded figure must round from the real one at its written precision, and stay within 5% | "£2.9m" for 2,892,000 is honest. "£1m" for 1.4m rounds correctly and still misleads |
| R3 | "half" and "a third" must be within one point of a real percentage, with no allowance for "nearly" | Hedging words are how a loose figure gets through |
| R4 | The check can't prove a true number sits on the right claim, so each section is checked against its own sources only | It narrows the risk. Consultant approval covers the rest |
| R5 | A draft paragraph must cite its sources, and its figures are checked against those sources only | A figure from elsewhere in the run is true but unsupported where it's used |
| R6 | One redraft with the failures listed, then the section keeps the engine's text | Repeated retries cost money and rarely help. A person is better value |
| R7 | Server-side refusal fallbacks are off | They'd move customer metadata to another model with nobody deciding, while zero data retention is still an open question (QUESTIONS.md). A refused section keeps the engine's text. Worth revisiting once that's answered |
| R8 | First and last names are masked in prompts as well, apart from a short list of ordinary words | `scrub()` catches full names only, and metadata labels such as "Sam's pipeline" hold first names |
| R9 | Evidence isn't sent to Claude | It isn't needed for wording, and a query can quote record values |
| R10 | Charts sit on a Carbon panel | Chartreuse is 1.5:1 on Ivory, which fails the chart contrast check. It's about 10:1 on Carbon |
| R11 | Poppins is embedded in PDFs from `@fontsource/poppins` (OFL), and only named in Word | PDF rendering mustn't need the network. A machine without Poppins shows Word's fallback font |
| R12 | A domain nobody assessed shows no issue count | "0 issues" would read as a clean result |
| R13 | Chromium only runs with the network off, and with routes other than `data:` aborted | A report holds customer data, and rendering has no reason to load or send anything |
| R14 | The number check runs again on printed page text, against the whole run | It catches anything a template adds after section checks, including chart labels. It's unscoped, so it's weaker than the section check |
| R15 | Deck density flexes in steps: more cards, then two columns, then one summary slide in place of domain openers. Tables are the last resort | 40 to 60 slides has to hold for a thin org and a huge one. Every step before the last keeps each issue's summary and recommendation. Only the last cuts anything, and it says so |
| R16 | A deck under 40 slides is flagged, never padded | Filler slides would be worse than a short report. The layout check reports it, and a consultant decides |
| R17 | Reports show overridden figures. Raw notes show the original with the override beside it | An executive reader shouldn't see a corrected number. The audit trail needs both |
| R18 | The pipeline deep dive adds open pipeline by stage, the delivery outlook, quarterly trends, where wins come from, where deals are lost, and close dates with stage speed. Sales cycle and slippage share a slide. In two-column densities, the deep dive pairs charts, and metric definitions and the after-90-days list go into columns | The deep dive took the deck past 60 for an ordinary org. Pairing keeps every chart, and the lists are reference. An ordinary org may now reach the domain summary step (R15), which still keeps every issue's summary and recommendation |
| R19 | The executive summary has a pipeline page after the scorecard: pipeline today, weighted value, expected value by month, and one line of potential revenue for each sizing rule, never totalled. The 90-day plan pages itself by measured line heights: later phases move to another page, and only when the plan wouldn't fit the pages left does it drop actions, from the longest phase first, each phase keeping at least one and the note that the full report has the rest | Long recommendations ran the plan into the footer. Moving a phase is better than cutting one, and the 8-page limit still holds |
| R20 | `compactMoney` rounds half up in decimal | `toPrecision` rounds the binary value, so £3,255,000 printed as £3.25m and failed the number check, which rounds half up |

| 47 | An org goes into the benchmark set at most once in any 4 quarters: `hc benchmark` refuses a run when another run of the same org in the same runs folder was exported within that window. `hc benchmark --summary` counts only rows in the 4 quarters ending at the newest period | The minimum group of 10 means 10 orgs, but rows can't be traced to an org, so they can't be de-duplicated afterwards. Refusing at export, where the org id is still known, and windowing the count means a repeat check a year on replaces an org's figures rather than adding a second org |
| 48 | The customer's name comes from the org's company information (`Organization.Name`) unless a run or intake gives one. It goes on the report covers and is registered with the pseudonymiser as a `customer` token, so it's masked before anything reaches Claude | Coby asked for the company information to be the name by default. The cover needs a name, and masking it keeps rule 7 for the customer as well as for people |
| 49 | Headcount bands are LinkedIn's company sizes (1-10, 11-50, 51-200, 201-500, 501-1000, 1001-5000, 5001+), and the intake records the LinkedIn URL, industry and headcount band. `hc benchmark` reads industry and headcount from the intake, and the flags only override it | Consultants read headcount from LinkedIn, so its bands avoid a conversion that can't be done (11-50 straddles 49 and 50). The URL is kept as the source. We don't scrape LinkedIn: it needs a login and its terms forbid it |
| 50 | Stale, past-close, ownerless and quiet open deals are sized as potential revenue: each deal's Amount at the share of comparable deals that still won, from `potentialRevenue` in `historic-pipeline/potential.ts`. Comparable means deals closed in the window, rebuilt from stage history, that were in the same situation while open: past the close date they had then (`dq.open-opps-past-close`), in one stage for 30 or 60 days (`cur.stale-deals`, `rev.stalled-deals`), with no change of any kind for 90 days (`dq.open-opps-no-activity`), or in the same stage (`dq.opps-inactive-owner`). Won is counted against won, lost and no decision. Below `minSample` comparable deals, a stale situation falls back to the org's own win rate, called a ceiling, and a stage isn't sized. The raw exposure, the deals with no amount and the period are stated, and no amount is imputed | The customer review: old opportunities are still potential opportunities. Exposure alone overstated them, and the average win rate flattered them. Past activity isn't in stage history, so no history row for 90 days stands in for no activity, and says so. When an owner left isn't in stage history either, so ownerless deals are compared by stage. A late stage can win more often than the average deal, so the overall rate is no ceiling there (rule 5). The five findings overlap, so they're never added together |
| 51 | The delivery outlook weights each open deal by its stage's win rate (DECISIONS 50's cohort, by stage) and places it in the month it's expected to close: its current close date, or its first close date moved by the median days won deals closed after their first date, whichever is later. A deal whose expected date has passed has no month and is shown apart. It covers this month and the 5 after it. Stages with too few closed deals aren't weighted, and too few won deals with history makes the outlook not measurable | It's for whoever staffs the work once it's won, so it's an expectation by month rather than a forecast by rep. Moving the first date by the median lateness, without going earlier than today's date, doesn't double-count a deal that's already been pushed. Overdue deals have no honest month, so they aren't spread across the next ones |
| 52 | New read: Opportunity `Id`, `AccountId`, `CloseDate` for wins before the analysis window (`prior-wins`). A won deal is from a repeat customer when its account had already won, before the window or earlier in it. Won means `IsWon` or a stage the calibration calls won. If the read fails, new and repeat are not measurable | Without earlier wins, every account's first win in the window would read as new, which is exactly wrong for a business built on repeat clients. Ids and dates only, SOQL through the existing route, so the allowlist is unchanged |
| 53 | A stage's win rate counts closed deals that were in that stage at some point, not those that reached it or later. Today's open deals by stage use a minimum of 10 deals for a stage's median age, not `minSample`. Top accounts are shown as cumulative shares, with accounts as tokens | "Were in it" handles retired and renamed stages without guessing where they sit. Today's open deals are the whole population, not a sample, so a smaller group is still exact, and 10 is where one deal stops moving it far. An account's name is never read |
