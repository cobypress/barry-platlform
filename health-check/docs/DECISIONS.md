## File storage

We recommend **AWS S3 in eu-west-2 (London)**, with default KMS encryption, Block Public Access on, and a lifecycle rule that deletes extracts 30 days after delivery.

- **Region:** London keeps data in the UK, which is the simplest story for a UK customer's security review.
- **Fits Vercel:** the browser uploads screenshots straight to S3 through a presigned URL, so the file never passes through a function's request size limit. The worker reads with its own credentials.
- **Deletion:** a lifecycle rule enforces the retention promise even if our own code fails.

Alternatives considered:

- **Vercel Blob:** private stores and region choice exist, but we couldn't confirm a London store, and the region can't be changed afterwards. Reads also go through a function.
- **Cloudflare R2 with EU jurisdiction:** a good fallback if AWS isn't wanted, but it's EU rather than UK.

## Connecting customer orgs

**Answer: yes, customer orgs need the External Client App installed from a managed package (2GP).** Checked on 2026-11-03 against Salesforce's help and guides. It hasn't been tried from a second org, because this work could only touch `bc-hc-dev` (QUESTIONS.md).

- **A local app only works in its own org.** "Local external client apps are available only on the org where you create them." ([Create an External Client App](https://help.salesforce.com/s/articleView?id=xcloud.create_a_local_external_client_app.htm&language=en_US&type=5)). "External client apps can't be used until they're installed in an org, unlike connected apps that can be used by any org without installation" (Canvas Developer Guide, API 68.0, `canvas_framework.pdf`). "Only packaged apps can be deployed to other orgs" ([Comparison of Connected Apps and External Client Apps](https://help.salesforce.com/s/articleView?id=xcloud.connected_apps_and_external_client_apps_features.htm&language=en_US&type=5)). Even the Salesforce CLI says it "requires an external client app in the org that you're authorizing" (SFDX Developer Guide, API 68.0).
- **Packaging means 2GP.** "Packageable apps are packaged with second-generation (2GP) managed packaging and distributed to subscriber orgs" ([External Client Apps](https://help.salesforce.com/s/articleView?id=xcloud.external_client_apps.htm&language=en_US&type=5)). 1GP is also allowed, and 2GP with a Dev Hub is recommended ([Configure Packageable External Client Apps](https://help.salesforce.com/s/articleView?id=xcloud.configure_packageable_external_client_apps.htm&language=en_US&type=5)).
- **The connected app route is closing.** Since early September 2025, a required, automatic restriction blocks new users from uninstalled connected apps, unless they hold Approve Uninstalled Connected Apps, which only the standard System Administrator profile gets automatically ([knowledge article 005132365](https://help.salesforce.com/apex/HTViewSolution?id=005132365&language=en_US)). A read-only integration user wouldn't hold it, so each customer would have to install the app from Connected Apps OAuth Usage anyway. From Spring '26, new connected apps can only be created through Salesforce Support, and "it is the ISV's responsibility to provide a migrated ECA version of their app" ([knowledge article 005228017](https://help.salesforce.com/apex/HTViewSolution?id=005228017&language=en_US)).

What it takes:

- A namespace, a Dev Hub with second-generation packaging switched on (it can't be switched off), and a managed package holding the app and Barometer Read Only. A version must be promoted before it installs in production; beta versions install only in scratch orgs and sandboxes (2GP guide, API 68.0).
- The Dev Hub should be a production or partner business org. The 2GP guide warns that if a package's Dev Hub "expires or becomes inactive, the installed package can't be updated", and Developer Edition orgs expire with inactivity. ISVs are told to define packaged apps in their partner business org. `bc-hc-dev` is fine for development, not for the package customers install.
- No security review is needed for a private, unlisted package. Customers see a notice at install that it hasn't been through one.
- Deleting the app in the source org breaks it in every customer org, because they depend on its global OAuth settings.
- The customer's admin controls the policies, which are never packaged: permitted users, IP relaxation, refresh token expiry, session timeout. Our install instructions should ask for "admin approved users are pre-authorised" with Barometer Read Only, so nobody else, administrators included, can authorise the app.

Still open: whether an API-only integration user can complete the interactive consent (QUESTIONS.md). If it can't, customers either use a full-licence user with only Barometer Read Only, or pre-authorise the integration user for JWT bearer, as `bc-hc-dev` does.
